## Decisions made today

- **Firestore writes sit behind a `CallStore` interface** in `services/pipeline/src/store/`: a Firestore implementation (Admin SDK, application default credentials) and a no-op one. `index.ts` uses Firestore when `K_SERVICE` is set (Cloud Run) or `STORE=firestore`; otherwise no-op, so local runs and tests don't write to the shared database. Writes are fire-and-forget: errors are logged, never thrown, never awaited before a `risk` message.
- **The scam type shown is the call's dominant type**, not the last tick's. The pipeline counts ticks per non-`none` type and reports the most frequent, ties going to the most recent. This fixes "police scam" in the warning against "Fake bank or BNM" on the hold screen. Only `session.ts` changes; the shared contract does not.
- **The dashboard gets its Firebase config at runtime** from Hosting's reserved `/__/firebase/init.json`, with `VITE_FIREBASE_*` variables as the local-dev fallback. No Firebase key is committed, so the secret scan stays clean.
- **Firestore rules:** read allowed on `sessions/**`, all client writes denied. The pipeline writes with the Admin SDK, which bypasses rules.
- **Spoken warning (T3.1) uses fixed lines recorded at startup.** Cloud Text-to-Speech with `modelName: gemini-2.5-flash-tts`, voice `Kore`, MP3 (API enabled 15 Oct; checked: ms-MY 6.6 s / 42 KB, en-US 4.9 s / 37 KB). Too slow to say Gemini's warning text live, so the pipeline records one fixed spoken line per (language, `strong_warning` | `hold_transfers`) at startup, keeps it in memory, and sets `audioUrl` to a `data:audio/mpeg;base64,...` URL on those `warning` messages. If recording failed, `audioUrl` is left out. No shared-contract change.
- **Parallel PRs don't touch `README.md` or `pnpm-lock.yaml`.** Dependencies land in T0; README rows are updated once at integration (T2.5).

## How the orchestrator skill is used

Today follows `.claude/skills/orchestrator/SKILL.md`. The main session (Opus) plans, decides, writes briefs, reviews diffs and deploys. Subagents do the building and the command-running.

| Task | Who | Why that model |
| --- | --- | --- |
| T0 groundwork, T0.4 rules deploy | Main session | Shared config and dependencies that every wave-1 brief builds on; a deploy |
| T1.A Firestore writes, T1.B dashboard, T1.D UI fixes | Sonnet, `isolation: "worktree"`, all three spawned in one message | Implementation where the design is decided above |
| T1.C health check | Sonnet, worktree, same message | Small, but needs judgment about network failures |
| T2 review, merge order, deploys, live check | Main session | Expensive if wrong; needs this session's context |
| T3.1, T3.2 contract and design | Main session, then a Sonnet brief each | ADR 6 and the shared contract stay with the main session |
| T4.1 secret scan | Haiku | One right answer: run gitleaks, report findings |
| T4.2 README | Main session draft | The judges read it; tone and accuracy matter |

**Briefs** use the skill's six parts (outcome, where, decided already, out of bounds, done when, report under 150 words). Every brief says: don't change `packages/shared`, `README.md` or `pnpm-lock.yaml`; report back if one needs changing.

**Review.** For each subagent: `git diff --stat` and the important parts of the diff, then `pnpm test` and `pnpm typecheck` in the main session after the whole wave, checked against the brief and the ADR rules in CLAUDE.md. Small fixes are made inline. A larger problem goes back to the same subagent once through SendMessage; if it fails again, the next model up or the main session takes it. No loops.

**Branches.** Each subagent's worktree branches from the T0.3 branch, so wave 1 doesn't wait for Ilham to merge T0.3. Each opens its own PR against `main`; once T0.3 is merged, those diffs shrink to their own work.
